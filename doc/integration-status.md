# FPGA—ARM 接口与联调状态

**尚未完成当前 AVM 核心与 ARM 应用的板级联调。** ARM 旧代码可以作为适配参考，但不代表 AVM 已实现其协议。

## 1. 接口对照

| 项目 | FPGA 当前 AVM | ARM 当前代码 | 缺口 |
|---|---|---|---|
| 输入帧 | 四路 RGB565，外部内存字节地址，配置尺寸/步长 | PCIe 或文件源统一使用 1280×720 RGB565 | 采集/帧存就绪条件与输入流选择 |
| 内存事务 | 16 字节对齐、128bit 读拍、单个在途、突发不跨 4KiB | 驱动 ioctl、BAR、`/dev/mem` 映射 | 物理 DDR 与 DMA 桥接 |
| 输出 | `m_valid/m_ready/m_pixel/m_sof/m_eol` | 四个固定帧缓冲及 read 状态码 | 像素流写帧、DMA、完整帧提交 |
| 配置 | `cfg_kind` 增益/Alpha/提交，帧边界原子更新 | 旧 I2C 图像模式控制 | 统一控制平面及版本 |
| 统计 | 四组交叠统计，Python 回放曝光反馈 | ADAS/检测结果对象 | ARM 曝光读回和配置驱动 |
| LED | 无板级 LED 控制接口 | ADAS `led_mask` 用于屏幕显示 | 实体 LED 寄存器及控制通路 |
| 时钟 | 核心时钟域接口 | Linux 线程/信号 | CDC、DMA 一致性、复位和异常恢复 |

## 2. ARM 旧协议事实

相关源文件为 `arm/src/hardware/pango_fun.*`、`pcie_frame_status.h` 和 `file_video_source.*`。

- 设备名 `/dev/pango_pci_driver`，ioctl 命令族 `'S'`，编号 0～11；另有 `/dev/mem` BAR 映射。
- read 返回的状态使用 `status > 0 && (status & 1)` 表示帧就绪，缓冲索引为 `(status >> 1) & 3`。这与普通 read 返回“有效字节数”的用法不同，驱动必须遵循同一约定。
- 接收内存为 `1280 × 720 × 2 × 4` 字节的四槽 RGB565。驱动如何写入、缓存一致性和帧释放需要与其源码核对；当前只提供 `.ko`。
- I2C 设备 `/dev/i2c-0`，地址 `0x66`；旧源选择寄存器 `0x01`、查询 `0x02`、功能寄存器 `0x03..0x06`。这些值没有对应的当前 `avm_core` 寄存器实现。
- 推理线程内部有三个任务槽，输入保留指针，任务槽忙时丢帧。与底层四槽循环写入之间尚未验证完整生命周期；Qt 信号本身不能保证源图在推理结束前不被覆盖。

## 3. 图像语义和测试边界

四相机 AVM 输出是地面投影。ARM 交通模型、车道线 ROI、导航面板位置等逻辑来自另一条透视/演示视频链路。集成时需明确保留前视流、送入鸟瞰流或增加独立通道，并重新验证检测模型和几何规则。

现有 ADAS 视频 E2E 测试直接调用车道线、导航和规则类，不经过 PCIe、Qt 线程、RKNN 模型和显示。因此该测试证明 CPU 链路在指定合成视频上的表现，不能证明整个应用或跨端传输可靠。

随工程导入的 ARM 板端记录当时未发现 PCIe 设备，并记录 I2C 权限问题。FPGA 网表功能仿真不包含 SDF、物理 DDR、PCIe 或真实相机。二者均不足以证明本系统已经上板。

## 4. 接通前必须形成的契约

1. 核实板卡原理图与实际传输拓扑，不从旧工程名推断当前器件。
2. 明确每条图像流的视角、尺寸、步长、RGB565 字节序、SOF/EOL/帧号。
3. 定义每槽的生产、提交、消费、释放状态及背压/丢帧策略，覆盖 DMA 缓存同步。
4. 提供驱动源码和版本、MMIO/寄存器表、错误与复位协议；统一 AVM 配置和曝光统计。
5. 对应到板级 RTL、CDC、DDR、管脚和时序约束，完成布局布线后再测整机性能。

本次目录整理只记录这些缺口，没有生成协议占位实现或把它们标成已完成。
